从一块 PCB 到一台双臂机器人——硬件开发与整机装配手记

首页项目

一句话总结： 这一阶段，我一边尝试把陪伴机器人的散件原型收拢到一块 PCB 上，一边完成七自由度双臂机器人第二台样机的初步装配，也重新认识了“设备参数看起来很强”和“真正适合项目”之间的差别。

# 这次同时推进了三件事

这段时间的工作看起来有些分散：画 ESP32 开发板、调麦克风、做 PCB Layout、修改关节模组 ID、组装双臂机器人，还要验证一台工业相机能不能用于缺陷检测。

但真正做下来，我发现它们都在解决同一个问题：怎么把已经验证过的模块，变成一套能够实际装起来、接起来并稳定运行的系统。

程序能运行只是第一步。硬件接口是否完整、元器件能否集成、关节模组是否正常、传感器提供的数据是否符合算法要求，这些问题都会决定项目最后能不能落地。

# 陪伴机器人低成本版本：不再靠开发板堆起来

陪伴机器人的低成本版本已经完成了一部分功能验证，但硬件仍然以多个开发板和模块拼接为主。这样的方案适合快速试验，却不适合作为最终产品：线束多、接口散，出现问题时也很难快速判断是哪一段链路出了故障。

因此，这一阶段我开始尝试把原本分散的元器件整合到同一块 PCB 上。

# 先把麦克风链路跑通

在正式整合之前，我先完成了麦克风接入测试。麦克风连接到 ESP32 相关电路后，系统能够正常获取音频并识别到语音输入。

这一步很重要，因为原理图不是凭空设计出来的。只有先在开发板环境中确认麦克风、电源和数据链路能够工作，后续画进 PCB 时才有可靠依据。否则，如果板子做出来以后没有声音，很难判断是器件选型、原理图连接、PCB 布线还是软件配置的问题。

# 第一次完整推进 PCB 设计

麦克风链路验证通过后，我开始继续完善 PCB 原理图。到原理图基本完成时，原先散落的主控、音频输入和相关接口已经能够在一张图里看清楚整体关系。

真正困难的部分从 Layout 开始。

原理图更像是在回答“这些器件应该怎样连接”，而 Layout 需要回答“它们在真实板子上应该放在哪里”。元器件位置、接口朝向、电源走线、地平面、音频信号受到的干扰，以及 PCB 能不能顺利装进外壳，都要在这一阶段一起考虑。

我之前没有完整画过多少 PCB，所以推进到 Layout 后速度明显慢了下来。很多在原理图里看起来很简单的连接，真正放到板子上时才会发现走线会交叉、接口位置不合理，或者器件之间需要留下更多空间。

不过，这也是从“会接模块”走向“会做硬件”的必经过程。开发板验证的是功能，PCB 设计考验的则是系统性。

# 七自由度双臂机器人：软件写好了，实机终于装起来了

另一条主线是七自由度双臂机器人。这是一套用于具身智能实验的双臂平台，两条机械臂都由多个关节模组组成，顶部还安装了视觉传感器，可以进一步开展抓取、检测和遥操作实验。

前一阶段，我已经完成了 VR 遥操作程序的主要开发，并在仿真环境中验证了基本控制效果。但第二台样机一直没有完整装起来，关节模组、控制板和 CAN-USB 通信板等硬件也没有完全到位，所以程序始终缺少实机验证条件。

这种状态很典型：软件侧已经走到了下一步，硬件侧却还没有形成一个可测试的系统。没有实机，坐标映射、关节方向、零点和实际跟手效果都只能停留在推测阶段。

# 修改关节模组 ID

开始装配前，需要先逐个检查关节模组，并为它们配置正确的 ID。

双臂机器人挂在同一条 CAN 总线上时，每个关节都必须拥有唯一地址。如果 ID 重复，控制端发送的一条命令可能被多个关节同时接收；如果编号与机械臂关节顺序不一致，软件中的 J1、J2、J3 也会和真实电机对应不上。

调试过程中，我先修改并核对了各个关节的 ID。进行单臂测试时，又发现其中一个关节模组无法正常工作，只能先单独拆出并交由供应方处理。

这个问题反而提醒了我：关节模组最好在装进机械臂之前逐个通电、通信和运动测试。 如果等整机安装完成后才发现某个模组损坏，拆装和排查都会麻烦得多。

# 从一堆零件到第二台样机

随后两天的主要工作就是装配。外壳、机械臂和实验台需要逐步组合起来，同时还要处理关节编号、线束连接和零点设置。

装配机器人并不是简单地把螺丝拧上。每增加一个关节，都要确认它的机械方向、通信状态和 ID 是否正确；左右两条手臂还要保持一致的编号逻辑，否则后续接入控制程序时很容易出现左右臂或关节顺序错位。

经过连续装配和逐关节测试，第二台样机终于完成了初步组装，并安装到实验台上。各关节重新设置了 ID，也完成了基础零点设置。

到这一步，之前写好的 VR 遥操作程序终于有了继续向实机迁移的条件。接下来需要先验证单关节和单臂，再逐步进入双臂协同，不能一上来就把仿真中的完整动作直接下发给真实机器人。

检查 CAN 通信
      ↓
单关节低速运动
      ↓
确认关节方向与零点
      ↓
单臂动作测试
      ↓
双臂协同
      ↓
接入 VR 遥操作

# 相机选型踩坑：有深度信息，不代表能做缺陷检测

这一阶段还测试了一台准备用于工业视觉项目的相机。它具备激光和深度相关功能，从参数上看并不简单，但实际配置后发现，手里的型号没有 RGB 输出模式。

这直接卡住了后续验证。

当前缺陷检测方案需要从彩色图像中提取表面纹理、颜色变化和缺陷轮廓。如果没有 RGB 图像，即使相机能够输出深度或轮廓信息，也无法直接替代彩色相机完成现有算法的输入需求。

这次问题并不是设备性能不够，而是设备能力与任务需求没有对应上。深度相机适合测距和获取空间轮廓，RGB 相机更适合观察颜色与纹理。两者都属于视觉传感器，但解决的并不是同一类问题。

以后再做相机选型，我会先把算法真正需要的输入列出来，再去核对具体配置：

  • 是否包含 RGB、深度或红外等所需图像模态；
  • 分辨率能否看清目标缺陷；
  • 帧率是否满足实时检测；
  • SDK 能否在现有系统和开发语言中使用；
  • 当前采购配置是否真的开放了对应功能。

尤其要注意，“这个型号理论上支持”和“手里的这台设备已经包含”并不是一回事。如果在采购和项目交接阶段没有确认清楚，问题最终就会推迟到软件联调时才暴露。

# 从模块可用到系统可用

这几项工作让我对“系统可用”有了更具体的认识。

麦克风能够识别语音，不代表陪伴机器人的硬件已经适合装进产品；VR 遥操作在仿真里能够运行，不代表真实双臂机器人已经具备测试条件；相机具有深度和激光功能，也不代表它能为 RGB 缺陷检测提供正确输入。

单个模块成功，只能说明局部方案成立。真正进入系统后，还要面对接口、供电、通信、装配、配置和上下游依赖。很多工程问题不是代码错误，而是两个都能正常工作的模块，在边界处没有对上。

这次最大的收获： 做系统集成时，应该尽早确认实物、接口和输入输出，而不是等所有软件都写完后，才发现验证所需的硬件条件并不存在。

# 写在最后

从画第一版 PCB，到逐个修改关节 ID，再到把第二台双臂机器人装上实验台，这一阶段做的事情没有特别炫目的算法，但每一步都在让项目从原型更接近真实设备。

接下来，一边要继续完成 PCB Layout，让陪伴机器人低成本版本拥有更整洁、可复现的硬件；另一边也要把已经在仿真环境中运行的 VR 遥操作迁移到真实双臂机器人上。

相比让一个模块第一次运行起来，我现在更关心的是：它能不能稳定地成为整个系统的一部分。
