返京后的三天——陪伴机器人验收、Luckfox 烧录与视觉项目重启

发表于2026-07-24本文字数2.7k字阅读时长2 分钟
  • RoastDuck
首页工作记录

一句话总结： 返京后的这一周只有三个工作日，我一边验收陪伴机器人的硬件并在 Luckfox Pico Ultra 与 ESP32-S3 之间摸索方案，一边重新推动停滞了一段时间的高校视觉检测项目。

# 连续二十天之后，先停下来两天

这周我回到了北京公司。周一和周四都申请了调休：周一恰好是我的农历生日，周四则是公历生日。之前连续上了二十天班，正好借这个机会让自己停下来缓一缓。

因此，这一周真正工作的时间只有三天。时间虽然不长，但返京后需要重新接上的事情不少，主要集中在两条项目线上：

项目 本周目标 当前结果
低成本陪伴机器人 验收物料，验证主控与基础软件 完成 Luckfox 固件烧录，并在 ESP32-S3 上跑通“小智”基础程序
高校视觉检测项目 恢复进度，准备真实样件测试 整理传送带与桌面方案，协调校方物料，并把样品寄给视觉厂商

这几天的核心不是把某个功能做到最终状态，而是先把停下来的工作重新组织起来，明确哪些链路已经具备条件、哪些问题需要外部资源配合。

# 陪伴机器人：先把到货物料验清楚

我不在北京的这段时间，陪伴机器人采购的物料已经陆续到货。返京后第一件事，就是对开发板和相关硬件做验收与基础测试。

陪伴机器人走的是低成本路线，硬件选型不能只看参数，还要看开发体验、系统完整度和后续维护成本。价格便宜的板卡，如果需要投入大量时间补齐系统和工具链，实际项目成本未必真的低。

这次首先测试的是 Luckfox Pico Ultra。它的价格确实有吸引力，但不像常见的成熟开发板那样上电就能直接进入完整环境，需要自己完成系统固件烧录。官方提供的是相对精简的 Linux 固件，基础功能有了，但距离顺手的开发环境还有一段距离。

我最终完成了固件烧录，确认板卡可以正常启动。不过受这一周时间限制，还没有继续开展上层应用开发。

选型心得： 开发板的成本不只是购买价格，还包括系统完善度、文档质量、工具链和调试时间。便宜的硬件，可能会把成本转移到开发阶段。

# Luckfox 之后，先用 ESP32-S3 验证交互方案

完成 Luckfox 的基础烧录后，我又转向 ESP32-S3 做快速验证，并把“小智”基础程序部署到了开发板上。

这一步的目的很明确：在 Linux 侧应用还没展开之前，先用更熟悉、启动更快的 ESP32-S3 验证陪伴机器人的基本语音交互链路。ESP32-S3 的算力和系统能力与 Linux 板卡不同，但它在成本、功耗、外设接入和快速原型方面更有优势。

本周暂时完成了“小智”的基础安装和启动验证。后续还要继续接入显示屏、麦克风等外设，才能判断这条方案是否适合最终样机。

现在两块板卡对应的是两种思路：

  • Luckfox Pico Ultra：具备 Linux 环境，扩展空间更大，但系统搭建和开发准备更重；
  • ESP32-S3：开发路径更轻，适合快速验证语音与外设交互，但资源边界更明确。

我不会只根据纸面参数立刻做最终决定，而是准备让两套方案都先走到可验证的节点，再根据功能、稳定性和成本做取舍。

# 高校项目：把停滞的视觉检测重新推起来

另一条工作线，是公司为高校推进的视觉检测项目。我离开北京期间，这个项目进展不多；返京后，公司重新开始推动，我也接着梳理当前状态和下一步条件。

视觉检测不能只在电脑里跑一段程序，它最终必须放进真实场景。因此，本周首先处理的不是算法细节，而是把测试环境需要的基础条件凑齐：

  1. 确认传送带、桌面等简单工装；
  2. 与校方沟通并获取对应物料；
  3. 整理待测样品和检测要求；
  4. 联系视觉检测厂商验证现有软件能否满足需求；
  5. 等待对方搭建场景并完成第一轮测试。

本周已经把物料寄给北京的视觉检测公司。对方还需要按照实际工况布置场景，测试完成后，我会再去现场看一遍效果。

如果这套软件无法满足要求，备选方案是使用西安伟景的产品。它的成熟度相对更有保障，但价格也更高。对当前项目来说，最理想的结果还是北京厂商能够完成工作：沟通和现场验证更方便，整体成本也更可控。

# 为什么要先看现场效果

视觉检测方案很容易在演示样品上表现良好，却在真实生产条件下暴露问题。光照变化、传送带振动、材料表面纹理、缺陷边界、相机安装角度和节拍要求，都会影响最终效果。

因此，我更关心的不是厂商给出的单次识别截图，而是它能否在接近真实场景的布置中稳定完成以下任务：

  • 样品连续通过时能否保持稳定识别；
  • 复杂纹理下会不会出现大量误检；
  • 缺陷边界不明显时是否仍有区分度；
  • 检测速度能否跟上传送节拍；
  • 软件接口是否便于后续接入整套设备。

这些问题只有把物料、相机、光源和传送机构放到一起，才能得到有意义的答案。

# 三个工作日的边界

这周完成的事情都停在“建立下一步条件”的位置：

  • Luckfox Pico Ultra 已完成固件烧录，但还没有展开应用开发；
  • ESP32-S3 已跑通“小智”基础程序，但外设联调还未开始；
  • 高校项目的样品已寄出，但视觉厂商仍在搭建测试场景。

这些不是最终成果，却是项目继续推进必须跨过的节点。硬件开发经常如此：一周的结果不一定是一个完整功能，也可能只是把系统从“没有条件验证”推进到“下一步终于可以开始验证”。

# 下一步计划

接下来会继续推进三件事：

  1. 在 Luckfox Pico Ultra 上补齐开发环境，开始验证上层应用；
  2. 围绕 ESP32-S3 接入显示屏和麦克风，继续搭建陪伴机器人样机；
  3. 跟进视觉厂商的场景测试，现场确认效果后决定是否采用当前方案。

如果北京厂商的测试结果不理想，再进一步评估西安伟景方案的性能收益是否值得更高的成本。

# 写在最后

返京后的这一周很短，节奏却很典型：一边是开发板烧录、程序验证这种亲手调试的工作，另一边是物料、工装、校方和供应商之间的协调。

工程项目很少只靠写代码往前走。很多时候，真正决定进度的是硬件有没有到、测试环境是否搭好、样品是否真实，以及外部方案能否在现场稳定运行。

先把条件准备好，再让每一次测试都回答一个明确的问题。
