工作日志（7月13日-7月19日）：机器人项目交接与青岛展会支持

本周是泰安机器人调试工作的收尾阶段。前两天的主要任务，是向新到泰安的同事交接机器人连接、远程开发、跌倒检测服务以及 App 配套功能的使用方法，确保我离开现场后，相关工作仍然能够继续推进。

完成交接后，我从泰安前往青岛，参加 APIE2026 第七届亚太国际智能装备博览会。工作内容也由前期的软件开发和机器人调试，转向了产品展示、现场操作与业务讲解。

# 泰安阶段收尾：机器人开发流程交接

由于我即将离开泰安，前两天的重点不再是继续增加新功能，而是将已经完成的工作交接给新到现场的同事。

交接内容主要包括：

  • 如何连接机器人；
  • 如何通过 VS Code 对机器人进行远程开发；
  • 跌倒检测代码所在位置及基本运行方式；
  • App 相关修改内容；
  • 跌倒检测和 App 配套服务的启动方法。

机器人开发主要采用 VS Code Remote-SSH。配置完成后，可以直接在本地 VS Code 中打开机器人上的工程目录，并在远程环境中编辑、运行和调试代码。

与传统的 SSH 终端操作相比，Remote-SSH 更适合持续性的开发工作。普通 SSH 通常需要在命令行中编辑代码，或者先在本地修改，再通过 SCP、SFTP 等方式上传到机器人。Remote-SSH 则可以直接使用 VS Code 的文件浏览、代码跳转、终端和插件能力，省去了反复上传、下载文件的过程。

整体工作方式可以概括为：

本地 Windows 电脑
        │
        │ VS Code Remote-SSH
        ▼
机器人 Linux 系统
        │
        ├── 直接编辑机器人端代码
        ├── 使用远程终端运行程序
        ├── 查看服务日志
        └── 调试机器人功能

这种方式不仅提高了开发效率，也降低了新同事接手项目的门槛。只要完成 SSH 配置，就可以在相对熟悉的 VS Code 环境中继续维护机器人代码。

# 跌倒检测与 App 功能交接

除机器人连接和开发环境外，我还对前期完成的跌倒检测功能进行了交接。

目前这部分工作已经形成了一条相对完整的运行链路：

机器人摄像头
    ↓
实时人体姿态与跌倒检测
    ↓
检测到跌倒事件
    ↓
向服务器发送报警信息
    ↓
App 弹出报警界面
    ↓
用户查看机器人实时画面并进行处理

我向同事介绍了跌倒检测代码的基本结构、相关配置文件以及启动方式，同时说明了 App 端修改涉及的功能和运行逻辑。

为了减少部署和使用过程中的操作步骤，我此前已经将相关程序整理成了一键启动方式。使用者不需要每次手动进入多个目录、配置环境变量并逐个执行命令，只需要运行对应的启动入口，即可启动跌倒检测及配套服务。

从开发角度看，功能“能够运行”只是第一步。项目要真正交付给其他人使用，还需要解决以下问题：

  1. 使用者能否快速找到程序入口；
  2. 各项服务是否有明确的启动顺序；
  3. 启动操作是否足够简单；
  4. 出现异常后是否能够查看日志；
  5. 新接手人员能否在没有原开发者现场指导的情况下完成基本操作。

一键启动脚本的价值就在于，将原本分散的启动命令、运行环境和配置过程封装起来，减少人为操作错误。对于需要在多台机器人上部署的项目，这种标准化也能降低后续复制和维护成本。

# 从“完成开发”到“完成交接”

这次交接让我更加明确地认识到，技术工作的完成标准并不只是代码写完、功能跑通。

如果一个功能只有开发者本人知道如何启动、如何修改和如何排查问题，那么它仍然具有较强的个人依赖。一旦开发者离开现场，其他人就可能因为不了解目录结构、运行环境或服务关系而无法继续使用。

因此，一个功能从开发完成到真正可交付，至少还需要经过以下几个阶段：

功能实现
  ↓
运行验证
  ↓
启动流程简化
  ↓
配置和代码整理
  ↓
使用方法交接
  ↓
其他人员独立运行

本周的交接工作，本质上就是将前几周完成的机器人功能，从“由我个人维护的开发版本”逐步转化为“其他同事可以接手的项目模块”。

目前的交接主要采用现场讲解和实际操作演示的方式。后续如果条件允许，还需要继续补充更加系统的文档，例如工程目录说明、服务启动方式、配置文件字段、常见故障以及日志查看方法。

# 前往青岛参加 APIE2026

完成泰安现场的阶段性交接后，周三我们乘坐高铁前往青岛国际会展中心，参加 APIE2026 第七届亚太国际智能装备博览会。

本次展会期间，公司主要展示了 110“热逆行”机器人。现场通过手柄控制机器人移动，并向参观人员展示机器人的基本运动能力和应用场景。

展会中的机器人演示和日常研发调试有明显区别。在研发环境中，我们更关注程序是否正确、接口是否正常以及功能是否能够运行；而在展会环境中，更关注的是设备能否稳定展示，以及参观人员能否在较短时间内理解产品的用途。

现场演示通常需要满足几个基本要求：

  • 机器人能够快速启动；
  • 手柄控制响应正常；
  • 移动过程保持稳定；
  • 展示流程简单、直观；
  • 出现问题时能够及时恢复；
  • 操作人员熟悉设备的基本状态和限制。

对于参观人员来说，他们通常不会关注代码结构或底层通信协议，而是更关注机器人能够解决什么问题、适用于哪些场景，以及实际操作是否稳定。因此，展会现场的技术支持不仅需要会操作设备，还需要将技术功能转换成更容易理解的产品语言。

# 了解工业零部件业务

除了机器人产品，公司还开展工业零部件生产相关业务。由于我此前的工作主要集中在机器人软件开发和功能调试上，对这部分业务了解得并不多。

借助这次展会，我对公司的工业零部件产品和业务方向进行了初步了解，并协助进行了部分现场介绍。

这一过程也让我接触到了研发工作之外的另一个视角。技术人员通常关注的是具体模块，例如模型、传感器、通信接口和控制程序；但从公司的整体业务来看，一个产品还涉及生产制造、供应链、销售、客户需求和现场交付。

了解这些内容有助于在后续开发中更准确地判断哪些功能真正具有落地价值，也能避免只从技术角度设计产品，而忽略实际使用和商业化过程中的约束。

# 连续工作的阶段性结束

展会于周日结束，随后我们返回北京。

从前往泰安出差、进行机器人调试，到完成项目交接并参加青岛展会，我已经连续工作了约 20 天。这段时间的工作内容跨度较大，包括摄像头调试、跌倒检测、服务器通信、App 功能修改、机器人部署、同事培训以及展会支持。

返回北京后，我申请了调休，准备对这一阶段的工作进行适当调整和休息。

持续推进项目固然重要，但长期连续工作也会明显影响注意力和判断力。特别是在机器人调试中，很多问题需要反复查看日志、检查网络、确认设备状态并排除软硬件故障。如果精力不足，很容易忽略细节，反而增加排查时间。

因此，合理休息并不是项目推进的中断，而是维持后续工作质量的一部分。

# 本周小结

本周的工作主要可以分为两个阶段。

第一阶段是在泰安完成机器人项目的阶段性交接：

  • 向新同事讲解机器人连接和基本操作方法；
  • 完成 VS Code Remote-SSH 开发流程的演示；
  • 交接跌倒检测代码及相关配置；
  • 说明 App 端修改内容和报警链路；
  • 演示跌倒检测及配套服务的一键启动方式。

第二阶段是前往青岛参加 APIE2026：

  • 参与 110“热逆行”机器人的现场展示；
  • 使用手柄控制机器人完成移动演示；
  • 协助向参观人员介绍机器人产品；
  • 初步了解公司的工业零部件生产业务；
  • 从产品展示和客户沟通的角度重新认识技术成果。

这一周没有继续开发大量新功能，但完成了一个项目中同样重要的环节：将已经实现的功能交给其他人，并让技术成果能够在开发环境之外继续运行和展示。

前几周的工作重点是解决“功能能不能做出来”，本周则更多是在解决“功能能不能被其他人接手”和“产品能不能被外部人员理解”。

从研发、部署、交接到展示，这几个环节共同构成了技术成果真正走向实际应用的过程。
